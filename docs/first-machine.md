# Your first machine

Create a small C++ instrument, play it in the browser, then change its pitch by
one octave. This path needs no firmware, Blackfin compiler or device. Run the
commands from the SDK checkout. The starter lives in its own source repository
beside the SDK, with agent instructions and CI generated by the SDK.

## Check your tools

Install [Python 3.11 or newer](https://www.python.org/downloads/),
[Node 22.12 or newer](https://nodejs.org/en/download), and
[LLVM](https://releases.llvm.org/download.html) with Clang's `wasm32` target and
`wasm-ld`. Use a recent Chrome or Edge for the workbench.

Create an isolated Python environment. On Windows PowerShell:

```powershell
python -m venv .venv
.venv/Scripts/python.exe -m pip install numpy==2.3.5
.venv/Scripts/python.exe sdk.py doctor --preview --cxx "C:/Program Files/LLVM/bin/clang++.exe"
```

On macOS or Linux, create it with `python3 -m venv .venv`, use `.venv/bin/python`
instead of `.venv/Scripts/python.exe`, and pass `--cxx /path/to/clang++` for your
LLVM installation. Apple's Xcode Clang lacks `wasm-ld`: on macOS install
Homebrew's `llvm` and `lld` and pass `--cxx "$(brew --prefix llvm)/bin/clang++"`.
The commands below use
`python` for that environment's interpreter; substitute its full path if you
have not activated it. Omit `--cxx` when the correct Clang is already on PATH.

The doctor must print **PASS: WebAssembly compilation, linking and execution**.
It actually compiles and executes a probe. A C++ compiler that works for desktop
programs may still lack WebAssembly support. If the probe fails, choose a Clang
installation containing `wasm-ld` and repeat it before creating the machine.

## Create and play

```sh
python sdk.py new --repository --id mymachine --name "My Machine" --out ../mymachine
python sdk.py preview --source ../mymachine --out local/my-preview-001
python tools/serve_harness.py --preview local/my-preview-001
```

Add the same `--cxx` option from the doctor to the `preview` command if needed.
The ID follows the [machine name rule](api.md#registration-boundary): a
lowercase letter, then up to 14 lowercase letters, digits or underscores. It
must differ from every [catalog](catalog.md) machine's.

`sdk.py new` starts a four-control synth with the stock header. Choose
`--controls 5`, `6`, `7` or `8` when the sound needs more controls; these use
the shared two-page header. Unused second-page columns repeat first-page
controls with one saved value. `--kind effect` starts a four-control send effect instead
(effects have no browser preview). Every starter has a sound check in
`tests/sound.cpp`. `--repository` also writes README.md, AGENTS.md, LICENSE,
.gitignore and a GitHub Actions workflow beside the machine. It creates files without running
`git init`, committing or contacting GitHub. Initialize Git in that folder when
ready. Omit the flag to create just a machine folder in an existing repository.
The workflow checks the root-level machine against SDK `staging`; pin a compatible
SDK commit when releasing. Read the
[core machines](https://github.com/etcetc000/open-xy-core-machines) as the worked
examples: Macro Osc for two-page synths, Karplus and 2op FM for four-control
synths, Ring Mod and Ping Pong for effects, and
Timestretch for sample engines. Sample engines use the public sample API;
`new` currently supplies synth and effect starters.

Open http://127.0.0.1:8917/. You should see **My Machine**, four controls
and the **Triangle** and **Pulse** presets. Use the on-screen keys
or `A W S E D F T G Y H U J K`; audio starts automatically. Start with a low
Volume setting. **Stop all** or Escape releases the notes.

**Blend** moves from triangle to pulse, **Width** changes the pulse's duty cycle,
and **Level** changes its output level. **Motion** changes the display animation.
The optional second page adds up to four teaching controls: **Drive**, **Crush**,
**Rectify** and **Smooth**, all off by default. On a two-page synth, pressing any
encoder switches the whole page; in the preview, editing a parameter selects
its page. Both rows stay in place.
The starter is a learning oscillator; its pulse needs band-limiting before use
as a production instrument.

## Make an audible change

Open `../mymachine/engine.cpp`. Inside `render()`, change:

```cpp
voice.phase += pitch[i];
```

to:

```cpp
voice.phase += pitch[i] / 2;
```

The supplied pitch is a phase increment for each sample. Halving it makes the
oscillator repeat half as often, lowering every note by one octave.

Stop the server with Ctrl+C, build into a new directory, then serve that snapshot:

```sh
python sdk.py preview --source ../mymachine --out local/my-preview-002
python tools/serve_harness.py --preview local/my-preview-002
```

Use the same `--cxx` option on this rebuild if you selected LLVM explicitly.
Reload the browser and play the same key. It should sound one
octave lower. Restore the original line and build another fresh snapshot to
undo the change. `tools/check_first_machine.py`, which CI also runs, makes this exact edit and
checks that A4 changes from 440 Hz to 220 Hz:

```sh
python tools/check_first_machine.py
```

That exercise also accepts `--cxx`. It uses temporary source directories and
does not change your machine.

## What you own

| File | Purpose |
| --- | --- |
| `definition.json` | Name, controls, page switching, presets and declared state sizes |
| `core.h`, `engine.cpp` | `Voice` and `Shared` state, lifecycle callbacks and the 64-sample render |
| `display.h`, `display.cpp` | Display state and drawing callback |
| `panel.svg.fragment` | Artwork; IDs carry the machine's ID (`<id>_panel`, `<id>_node_N`, `<id>_palette_N`) |
| `machine.json` | Kind and SDK version, used by a [firmware build](build.md#3-add-your-machine) of the folder, which gives the machine its numbers |
| `tests/sound.cpp` | The machine's own host checks; extend them as the sound grows |

`python sdk.py test --machine ../mymachine` checks a machine folder the way
a machine repository's CI does: its records and sources, a preview build and
its `tests/*.cpp`, compiled with a host C++ compiler (`--host-cxx`, default
`c++`). It also prints a [CPU estimate](api.md#cpu) next to the core
machines'; keep it within their range. `--firmware` adds a native compile of
the machines given.

Change labels and presets directly in `definition.json`; custom previews read it
when building, with no separate JavaScript definition generator. Parameter
order determines the C++ control indices. See the [engine API](api.md) for
buffer ownership and the [display API](display.md#two-page-header) for the shared
header. Keep parameter captions in real units and artwork below the header at
y=38. The [UX conventions](ux.md) and Macro Osc are the layout reference.

Keep callbacks bounded: no allocation, blocking, logging, I/O, OS headers or
platform conditionals. The SDK supplies the adapters and memory. A custom
preview compiles `engine.cpp` and `display.cpp` through those adapters; additional
implementation code must be included by them. Includes must name local machine
headers or SDK `opxy/*.hpp` headers. Keep compiled output outside the source
directory, and use the SDK server rather than serving the checkout root.

## Hardware and publication

After host checks and audition, build a development image for your own XY
([building firmware](build.md#3-add-your-machine)). Keep all firmware and stock
content outside every checkout and use a fresh output folder. Preserve machine
numbers with the previous build's `--layout`. A
[personal kit](builder.md#export-a-kit) supplies the browser installation guide.

Follow [hardware profiling](profiling.md) before claiming measured CPU cost or
preparing a catalog submission. Commit the machine, build with profiling enabled,
install when authorized, confirm the device has rebooted, then collect a run
([one is enough](profiling.md#collect-a-run)) and generate the readout. Host estimates are useful during iteration;
they do not establish device timings. If hardware is unavailable, keep hardware
validation pending and ask a maintainer to measure it.

When publication is requested, follow [catalog submission](catalog.md#submit-a-machine):
reserve an ID, tag the measured commit and submit its release and CPU record in
one catalog entry against `main`. The machine code stays in your repository.
Every new or changed draft/published entry requires measurements for that exact
revision. Published community machines link to their pinned source in the builder.

## When a command fails

| Message or symptom | Next action |
| --- | --- |
| Compiler cannot build WebAssembly | Run `doctor --preview` with the exact `--cxx` path used for the build |
| Output already exists | Choose a fresh output suffix; existing source and builds are never overwritten |
| Preview is stale | Rebuild after source edits, restart the server with the new output and reload |
| Declared size differs from C++ type | Update the corresponding size/alignment in `definition.json` after changing state |
| Peak or drawing check fails | Correct the callback or its declared contract; the build prints the failing check |
| No sound | Unmute audio if needed, check Volume and Level, then play a key; the workbench status reports audio errors |
| Address already in use | Stop the previous server, or pass `--port 8937` and open that port |

Local authoring permits different sounds and drawings while running the shared
callback checks described in the [preview guide](preview.md). It does not
allocate a native engine ID or produce an installable machine. To put it on
the device, [build your own firmware](build.md#3-add-your-machine).
